=============תרחישים===============
א---
        ### 1. scale
1. הפקודה מגיעה ל-API server, שהוא ערוץ התקשורת, והוא רושם ב-etcd שצריך להיות 4 pods.
2. controller manager, שאחראי לבדוק כל הזמן שרץ המספר הנכון של pods, רואה שרצים רק 2 ובטבלה כתוב 4, אז הוא יוצר 2 pods חדשים.
3. scheduler מחליט באיזה node ירוץ כל pod חדש.
4. kubelet באותו node רואה שיש לו pod חדש, ונותן הוראה ל-container runtime להריץ אותו.
5. container runtime מריץ את הקונטיינר.
6. kubelet מדווח ל-API server שה-pods רצים, ועכשיו יש 4 pods ב-Running.


ב----
    ### 2. שלוש בלילה
אם הקונטיינר קרס: ה-pod עדיין קיים, ו-kubelet באותו node רואה שהקונטיינר לא עובד כשורה ונותן הוראה ל-container runtime להפעיל אותו מחדש. זה קורה באותו pod ובאותו node, בלי ה-scheduler.

אם מישהי מחקה את כל ה-pod: controller manager רואה שיש פחות pods ממה שצריך ויוצר pod חדש, scheduler מחליט באיזה node הוא ירוץ, ו-kubelet באותו node מפעיל אותו (דרך container runtime) ובודק שהוא אכן רץ.

ג----
    ### 3. node נכבה
ב-cluster בענן: ה-pods שרצו על node 2 נעלמים יחד איתו. ה-kubelet של node 2 מפסיק לדווח, וההנהלה מבינה שה-node לא זמין. controller manager רואה שחסרים pods ויוצר חדשים במקומם, scheduler שולח אותם ל-node 1 ול-node 3, וה-kubelet שם מפעיל אותם. אחרי כמה דקות כל ה-pods רצים שוב על ה-nodes שנשארו.

ב-Docker Desktop: יש מחשב אחד בלבד, שהוא גם ההנהלה וגם ה-node. אם הוא נכבה, הכול נופל: אין node אחר להעביר אליו את ה-pods, ואין הנהלה שתשים לב. רק כשמדליקים אותו שוב, ה-cluster עולה, וה-Deployments יוצרים מחדש את ה-pods.

ד-----
        ### 4. מהכיתה לענן
imagePullPolicy: Never — אומר ל-Kubernetes להשתמש רק ב-image שכבר נמצא על המחשב, בלי להוריד אותו. בכיתה זה עבד כי בנינו את ה-image על המחשב שלנו. ב-EKS ה-nodes הם מחשבים של אמזון, וה-image לא קיים עליהם, אז ה-pods לא יעלו (ErrImageNeverPull).
מה לשנות: להעלות את ה-image למאגר באינטרנט (registry, כמו Docker Hub או ECR), לכתוב ב-image את הכתובת שלו במאגר, ולהוריד את imagePullPolicy: Never.

Service מסוג NodePort — פותח פורט (כמו 30090) על כל node. בכיתה נכנסנו דרך localhost:30090, כי ה-node היה המחשב שלנו. ב-EKS ה-nodes הם מחשבים של אמזון ברשת שלהם, הכתובות שלהם יכולות להשתנות, ואין כתובת ציבורית אחת קבועה שמשתמשים יכולים להיכנס אליה.
מה לשנות: לשנות את סוג ה-Service ל-LoadBalancer. אז אמזון יוצרת כתובת ציבורית קבועה אחת, שמחלקת את המשתמשים בין ה-pods.

ה-----
    ### 5. pod בודד
pod של kubectl run נוצר בלי Deployment, אז אין מי שיחזיר אותו כשהוא נמחק. ל-web יש Deployment, ולכן ה-controller manager רואה שחסר pod ויוצר חדש.
כדי ש-stats יחזור תמיד: ליצור לו Deployment עם replicas: 1.
